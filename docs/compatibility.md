## Observations

**Engine API differences**

- Model lifecycle: 0.6.5 uses `POST {base}/models {"model": id}` (SSE progress, final `{"loaded": true}`) and `DELETE {base}/models?modelId=id`. 1.0.27 answers `404 {"statusCode":404,"message":"not found"}` to both and instead takes `PUT {store}/models {"id": id, "action": "load"|"unload"}` (same SSE progress stream, `{"unloaded": true}` on unload). Auto-load on the first chat completion works on both engines.
- Thinking: on 0.6.5 the reasoning is inline; `/no_think` in the system prompt suppresses it but every reply still starts with an empty `<think>\n\n</think>` block (also inside the tool-call `content` and the streamed first delta), so clients must strip it. On 1.0.27 `enable_thinking: false` removes reasoning entirely and `content` is clean; with thinking on, reasoning arrives in `message.reasoning_content` / `delta.reasoning_content`, never in `content`.
- 1.0.27 `GET /models` adds `family` (`qwen3`, `qwen35`, `smollm3`, `llama`), `supported_parameters` (`["tools","tool_choice","parallel_tool_calls"]` for Qwen3/Qwen3.5, `["tools","tool_choice"]` for SmolLM3, `null` for SmolLM2) and `reasoning`. The `reasoning` block is unreliable: it says `can_disable: false` for every thinking model although `enable_thinking:false` disabled thinking in all tests, and it flags the non-thinking `qwen3-4b-instruct-2507` as `supported: true, default_enabled: true`. `max_context` is 12032 on 1.0.27 vs 12000 on 0.6.5 for the same store setting.
- 1.0.27 `usage` carries `ttft_ms`, `decode_token_per_second` and `prompt_tokens_details.cached_tokens`; 0.6.5 only `token_per_second`. 1.0.27 reuses the prompt prefix across requests (`cached_tokens: 805` on the 821-token tool prompt), so the six tool prompts took 0.6-1.2 s each after the first, versus 3.0-3.5 s (4B) and 5.2-5.5 s (8B) for every prompt on 0.6.5, whose constant latency shows no sign of prefix reuse (0.6.5 reports no `cached_tokens`).
- Streaming: 1.0.27 emits a tool call as one complete delta (`id`, `name`, full `arguments`) in ~6 chunks and includes `usage` in the stream; 0.6.5 streams the `<think>` block first, then a tool-call delta with `arguments: ""` followed by argument fragments (16-22 chunks), also with `usage`. Tool-call ids are `tool_0` on 0.6.5 and `call_0_xxxxxxxx` on 1.0.27.
- 1.0.27's gateway enforces a 300 s serverless timeout per request and logs `unload_model: sessions still active` when a model is unloaded during an in-flight request, but the unload still completes (worker process terminated, ~13 s).

**Model behaviour**

- Qwen3-4B, Qwen3-4B-Instruct-2507 and Qwen3-8B: 6/6 on both engines, arguments always valid JSON matching the schema, `ping` probe structured, clean round trip (all five file names listed). The only non-"correct" picks were `list_files` first on prompt (c) (Instruct-2507 on both engines, 8B on 0.6.5) which an agent loop then follows with `read_file`.
- Qwen3.5 (`qwen35` architecture): 0.6.5 fails to load with `HTTP 500 {"message":"llama_model_load_from_file error: unable to load model","statusCode":500}` in 0.16 s (twice). On 1.0.27 both 4B and 9B load (`n_ctx_train` 262144) and, contrary to the expectation of XML in `content`, every tool call came back as structured `tool_calls` (ping, 6/6, round trip clean, no `<tool_call>`/`<function=` text anywhere). With thinking on they reason briefly (~60 tokens in `reasoning_content`) and still emit a tool call (`list_files` first, i.e. "check the file exists"), whereas Qwen3-4B with thinking on spends the whole 600-token budget reasoning and never calls a tool on either engine (finish_reason `length`); Qwen3-8B on 0.6.5 reasoned ~590 tokens and then called `run_python` (28.7 s). For agent use keep thinking off on Qwen3, or budget well over 600 tokens.
- SmolLM3-3B is engine-dependent. On 0.6.5 (`chatTemplate: "chatml"` in `GET /models`, i.e. the GGUF's own template is not used) it is given llama.cpp's generic tool format: the model answers with `{"tool_calls": [{"name": "ping", "arguments": {}, "id": "call_1___"}]}` or `{"response": ...}` as plain text in `content` (never structured), `/no_think` is ignored in 5/6 tool prompts, and it scored 1/6. On 1.0.27 it produces structured `tool_calls` with valid arguments (5/6, ping ok) but calls `mimoe_status` on "Hello, who are you?" with garbage trailing text, and the round trip fails: after the tool result it returns `{"name": "list_files", "arguments": {"path": "."}}` as content instead of an answer.
- SmolLM2-360M cannot tool-call on either engine (1/6 both, ping never structured): on 0.6.5 it emits invented JSON (`"arguments": {"arg1": "some_value"}`), on 1.0.27 it refuses ("as an AI, I don't have the capability to make calls") and hallucinates answers ("sales.csv has 10 rows and the total revenue is 10000"). It is fast (135-151 tok/s, TTFT 0.08-0.45 s) but only usable for plain chat.
- TTFT on the 821-token 8-tool prompt is prompt-processing time: 2.5-3.2 s for the 4B models on both engines (M1 Pro Metal), 4.3 s for 8B on 0.6.5. Decode: Qwen3-4B 39.6 tok/s (0.6.5) vs 32.9 tok/s (1.0.27, `decode_token_per_second`), Instruct-2507 39.7 vs 36.1, SmolLM3 53.9 vs 52.0, SmolLM2 135.5 vs 150.8, Qwen3-8B 23.5 on 0.6.5.

**Host incident (see `incidents` in compatibility.json)**

- At 07:16Z another local client sent a chat completion to 0.6.5 that auto-loaded `qwen3-4b` (Metal_Mapped 2376 MiB) while this probe had `qwen3-8b` loaded on 1.0.27. Both engines then hit Metal `Insufficient Memory (kIOGPUCommandBufferCallbackErrorOutOfMemory)`; the 0.6.5 engine process (`mimoe`, pid 84992) aborted with SIGABRT at 00:21:00 -0700 and port 8083 stayed closed, so `qwen3-4b` could not be reloaded on 0.6.5 at the end (the mimOE Studio app itself is still running and needs its engine restarted).
- The host stayed in heavy swap afterwards (7.4-8.3 GB swap used, <1 GB unused), so 1.0.27's numbers for qwen3-8b (0.9-1.0 tok/s, TTFT 32-55 s, thinking-on timed out twice at 240 s with `llama_decode failed (ret=-3)` in the log), qwen3.5-4b (5.7-6.1 tok/s) and qwen3.5-9b (3.3 tok/s) are memory-starved measurements, not engine speed; their functional results (loads, thinking control, tool calls, round trip) are valid. A 5-6 GB model plus ~1.5 GB KV/compute on a 16 GB Mac with a VM and browsers open is what tipped it over.

**Recommendation**

- Default for a CPU-only Windows laptop: `qwen3-4b-instruct-2507` (Q4_K_M, 2.5 GB). It scored 6/6 on both engines with structured tool calls and a clean round trip, has no thinking mode to manage (no `<think>` litter, no reasoning budget to tune), is the same size and speed as `qwen3-4b`, and loads on both engine generations. SmolLM3-3B saves 0.6 GB but its tool calling depends on the engine and breaks on the second turn; SmolLM2-360M cannot tool-call; Qwen3-8B needs 5 GB plus cache and is ~40 % slower per token; Qwen3.5 does not load on 0.6.5. (Absolute CPU tok/s were not measured here; only Apple-Silicon Metal numbers are in the tables.)
- Default for Apple Silicon (16 GB): the same `qwen3-4b-instruct-2507` (39.7 tok/s, 2.7 s TTFT on the 8-tool prompt). Offer `qwen3-8b` (6/6, 23.5 tok/s, 4.3 s TTFT, 5 GB) as an opt-in for users with 16 GB and nothing else open, and `qwen3.5-4b`/`9b` only for 1.0.27 users (structured tool calls, brief reasoning, but they never load on 0.6.5). Keep thinking off for tool use; if `qwen3-4b` (thinking variant) is chosen, strip the empty `<think></think>` block on 0.6.5 and never rely on the 600-token budget with thinking on.
